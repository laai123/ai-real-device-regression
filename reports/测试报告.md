## 一、测试范围

按需求排除了「历史记录」和「烹饪知识」两个模块，其余全部覆盖：

| 模块 | 覆盖内容 |
|---|---|
| 启动与首页 | 冷启动、五个入口卡片、退出登录入口、页面返回 |
| 菜谱选择 | 菜谱总数、8 个分类筛选、关键词搜索（空态） |
| 菜谱详情 | 基本信息、食材清单、烹饪步骤、评分标准 |
| 烹饪流程 | 模式选择弹窗、食材选择、步骤推进、校验拦截、计时器、返回确认、厨具提示 |
| 结果页 | 六项评分、总分、等级、点评、保存记录、返回首页 |
| 厨房设置 | 四种厨房类型、工具勾选、保存落盘 |
| 个人信息 | 昵称、辣度/甜度/咸度、忌口、保存落盘 |
| 数据与安全 | 账号存储、安装包配置、41 份菜谱数据一致性 |

**测试方法**：界面行为用 ADB 驱动真实设备点击（控件定位优先用 resource-id，其次用文本），
断言依据不是"看起来对不对"，而是拿菜谱 JSON / user_config.json / users.json 里的
真实数据与界面显示逐项比对。走流程的菜谱抽样 4 道：麻婆豆腐（川菜）、番茄炒蛋（家常菜）、
红烧肉（家常菜）、凯撒沙拉（西餐），覆盖中式炒制与西式凉拌两类差异较大的流程。

## 二、结论

功能主链路是通的：能选菜、能选烹饪模式、能一步步选食材和做法、能出结果页并保存记录，
首页/列表/详情/设置各页面都能正常进出。**但"数据"与"界面"之间存在大量对不上的地方**，
其中 5 个问题会直接让用户看到错误的分数、或者被一段自相矛盾的提示挡住。

### 必须优先修（P0，5 项）

| 编号 | 问题 | 影响 |
|---|---|---|
| D2 | 结果页评分分母写死，出现 `30/20`、`25/10` | 用户看到得分率 150%、250%，评分子系统等于失效 |
| D1 | 助手模式丢弃了大部分烹饪步骤 | "学习正宗做法"的核心卖点不成立 |
| I4 + D3 | 3 种食材没有可选项，但校验仍要求"为每种食材选择" | 引导语与校验互相矛盾，用户被卡在第 1 步 |
| I1 | 密码只用 Base64 存储（等于明文） | 账号安全 |

### 建议尽快修（P1，12 项）

设置类保存全部无效（厨房设置、口味偏好、忌口修改后不落盘）、列表页菜谱数与分类数对不上、
详情页步骤编号从"步骤4"开始、安装包是 debuggable、5 道菜在应用里根本不存在、
11 个菜谱存在重复选项 id、4 个菜谱评分满分不是 100。

### 可以排期（P2/P3，5 项 + 2 项提示）

难度分级只用到了 1~3 档、忌口为空时打印 `[]`、昵称有两套数据源、满分 100 分实际不可达、
`tips` 文案键名拼写为 `poose`、`cuisine` 与 `category` 两套分类字段口径不一致。

## 三、缺陷明细

### P0-1（D2）结果页评分分母被写死，出现得分率超过 100% 的显示

**现象**：结果页六项评分的分母固定为 `15 / 25 / 20 / 20 / 10 / 10`，与菜谱数据里
`scoring` 字段定义的满分完全脱钩。当数据里的满分比这个固定值大时，界面就会出现
分子大于分母的荒谬数字。

**实测证据**：

| 菜谱 | 结果页实际显示 | 数据里 scoring 定义的满分 |
|---|---|---|
| 麻婆豆腐 | 刀工 10/15、调味 25/20 | 刀工 10、调味 25 |
| 番茄炒蛋 | 刀工 10/15、调味 25/20 | 刀工 10、调味 25 |
| 红烧肉 | 刀工 10/15、调味 25/20 | 刀工 10、调味 25 |
| 凯撒沙拉 | 刀工 **5/15**、火候 **5/25**、调味 **30/20**、时间 **25/10** | 刀工 5、火候 5、调味 30、时间 25 |

凯撒沙拉那三个加粗项分别对应 **33%、20%、150%、250%** 的得分率。
四道菜的分母取值集合完全相同，可确认是代码里写死的常量，不是从数据算出来的。

**根因推测**：结果页展示层直接硬编码了六个维度的满分，而算分用的是菜谱数据里的分值，
两边各写一份、没有共用同一个来源。

**建议**：结果页每一项的分母改成从 `recipe.scoring` 实时读取；同时加一道校验，
分子超过分母时打日志并按分母截断，避免再出现"超过满分"的显示。

### P0-2（D1）助手模式丢弃了大部分烹饪步骤

**现象**：「助手模式」的文案是"跟着标准步骤走，学习正宗做法"，但界面只呈现
「食材准备 + 固定的一两个步骤」。菜谱数据里定义的步骤大部分被静默跳过。

**实测证据**：

| 菜谱 | 数据里定义的步骤 | 界面实际呈现 | 被丢弃的步骤 |
|---|---|---|---|
| 麻婆豆腐 | 焯豆腐、炒肉末、炒豆瓣酱、调味、出锅（5） | 食材准备、炒肉末、调味、出锅（4） | 焯豆腐、炒豆瓣酱 |
| 番茄炒蛋 | 打蛋、炒蛋、炒番茄、调味、出锅（5） | 食材准备、调味、出锅（3） | 打蛋、炒蛋、炒番茄 |
| 红烧肉 | 焯水、炒糖色、煸炒五花肉、炖煮、调味、收汁出锅（6） | 食材准备、调味、收汁出锅（3） | 焯水、炒糖色、煸炒五花肉、炖煮 |
| 凯撒沙拉 | 处理食材、面包丁、调凯撒酱、拌匀、装盘（5） | 食材准备、装盘（2） | 处理食材、面包丁、调凯撒酱、拌匀 |

被保留下来的步骤名在各菜谱里高度一致（基本都是"调味""出锅"这类通用步骤，
麻婆豆腐额外保留了"炒肉末"），而被丢弃的都是各菜谱特有的工艺步骤。这说明过滤
依据很可能是**步骤的英文 key 白名单**（如只认 `seasoning` / `finish`），
而不是步骤本身的有效性——这些被丢弃的步骤在数据里同样有 2~3 个可选项和完整的
小贴士文案，是完全没有被用到的高质量内容。

**影响**：用户照着做会漏掉焯水、炒糖色、炖煮这些关键环节；同时"步骤顺序(20分)"
这个评分维度因为步骤数被缩减而基本失去区分度。

**建议**：把过滤逻辑改为"渲染数据里定义的全部流程步骤"；如果确实只想呈现部分步骤，
至少要按菜谱配置，并把跳过的步骤在"菜谱详解"里以资料形式补全。

### P0-3（I4 / D3）食材没有可选项，但校验仍要求为它选择

**现象**：菜谱数据里有 3 个食材的 `options` 是空对象 `{}`。烹饪第 1 步会渲染出这个
食材的名称和图标，但下面一个选项都没有。而当用户点「下一步」时，弹出的是
**「请为每种食材选择处理方式」**——用户永远无法为一个不存在的选项做出选择。

**实测证据**：

| 菜谱 | 无选项的食材 |
|---|---|
| 麻婆豆腐 | 郫县豆瓣酱 |
| 红烧肉 | 调料 |
| 糖醋排骨 | 糖醋汁 |

`麻婆豆腐.json` 原文：`"doubanjiang": {"name": "郫县豆瓣酱", "icon": "🫙", "amount": "2勺（约30g）", "options": {}}`

**影响**：第 1 步的提示语自相矛盾，用户不知道该怎么继续。虽然实测在某些菜谱上
仍能推进（说明校验对空组是宽松的），但这段提示会把用户引向错误的方向。

**建议**：两条路都行——要么给这 3 个食材补上选项数据，要么在渲染时跳过 `options` 为空的食材，
并把提示语改成"请为每种食材选择处理方式（部分食材无需选择）"。

### P0-4（I1）账号密码只用 Base64 存储

**现象**：`files/data/users.json` 里密码字段存的是 `"MTIzNDU2\n"`，Base64 解码即得明文 `123456`。
Base64 是可逆编码，等同于明文存储。

**证据**：
```
{ "user_id": 1, "username": "test", "password": "MTIzNDU2\n", "created_at": "2026-07-17" }
```
另外值尾部多了一个换行符 `\n`，说明编码/写入环节还带着一个数据不干净的小问题。

**建议**：改为加盐哈希（bcrypt / Argon2 / PBKDF2），并去掉尾部多余字符；
登录校验用哈希比对而不是解码比对。

### P1-1（F2 / G4 / G3）设置类保存全部无效

**现象**：个人信息页和厨房设置页点「保存设置」后，**弹出成功提示并返回首页，
但配置文件完全没有变化**。

**实测证据**（三个独立操作都复现）：

| 操作 | 保存前 | 保存后 |
|---|---|---|
| 厨房设置选「西式厨房」并勾选第一个工具 | kitchen_type=chinese, tools=[] | kitchen_type=**chinese**, tools=**[]**（无变化） |
| 个人信息选「重辣」 | spice_level=适中 | spice_level=**适中**（无变化） |
| 个人信息输入忌口 `aaa,bbb,ccc` | dislike=[] | dislike=**[]**（无变化） |

日志里没有异常（`logcat` 只有一条 "Toast already killed. pkg=com.example.kitchenassistant"，
说明确实弹了提示），等待 6 秒后再次读取配置文件依然没变，排除异步写入的可能。
同时确认应用私有目录下**没有任何其它文件**记录这些设置。

**影响**：用户的厨房配置、口味偏好、忌口设置**重启应用后全部丢失**，
而这些恰恰是"个性化推荐"依赖的输入。

**建议**：检查保存逻辑是否只更新了内存对象却漏了写盘（或写到了错误路径）；
建议引入统一的数据存取层，保存后立刻回读校验一次并打日志。

### P1-2（A2）首页「退出登录」按钮尺寸为 0，用户无法退出

**现象**：首页界面树里存在 `tv_logout` 节点（`clickable=true`），但 `bounds=(0,0,0,0)`，
宽高为 0，即界面上看不见也点不到。首页也没有溢出菜单或其它退出登录入口。

**建议**：给该控件正确的布局位置（或放进右上角菜单），并补一个"退出后回到登录页"的回归用例。

---

### P1-3（B2）分类筛选与菜谱数据不符，且分类计数虚高

**现象**：8 个分类标签里 2 个有问题。

**实测证据**：

| 分类标签 | 顶部计数文案 | 实际列出 | 数据里 |
|---|---|---|---|
| 川菜 | 共 13 道菜 | 13 | 12 |
| 湘菜 | 共 4 道菜 | 4 | 5 |
| 韩餐 | 共 **3** 道菜 | **2** | 2 |
| 其余 5 类 | 一致 | 一致 | 一致 |

具体差异：
- **辣椒炒肉** 出现在「川菜」分类里，但它的数据是 `cuisine=湘菜`，导致川菜多 1 道、湘菜少 1 道。
- **韩餐** 顶部写"共 3 道菜"，实际只渲染出 2 道（韩式烤肉、泡菜汤），计数与实际条目对不上。

**建议**：分类过滤和计数都改成从同一份数据实时计算；辣椒炒肉补上正确菜系或修正过滤映射。

---

### P1-4（B1 / I6）菜谱数量三处对不上，5 道菜在应用内不存在

**现象**：三个来源的菜谱数量互不相同。

| 来源 | 数量 |
|---|---|
| 列表页顶部显示 | 共 **42** 道菜 |
| 设备上实际的菜谱数据文件 | **41** |
| APK `assets/data/recipes/` 内置 | **46** |

**证据**：APK 内置但设备上没有的 5 道菜是
**法式蜗牛、糖醋里脊、韩式拌饭、韩式炸鸡、麻辣香锅**——它们在应用里任何入口都找不到
（菜谱初始化时没有落到设备上）。列表页的 42 与韩餐分类的"共 3 道"很可能就来自
这批"计数里有、文件没有"的幽灵数据。

**建议**：修正初始化流程（把 assets 全量复制后再标记完成），计数统一按实际可用的菜谱算。

---

### P1-5（C1）详情页步骤缺失，编号还从「步骤4」开始

**现象**：菜谱详解页的「烹饪步骤」区块只列出 3 条，而且编号直接跳到 4。
`麻婆豆腐` 详情页实际渲染的是：

```
步骤4：炒肉末
步骤5：调味
步骤6：出锅
```

数据里定义了 5 个步骤（焯豆腐、炒肉末、炒豆瓣酱、调味、出锅），步骤 1~3 完全没有出现，
也没有任何"前 3 步见上文"之类的说明。

**根因推测**：内部步骤模型其实是完整的 6 项（食材准备 + 5 个流程步骤），
展示层过滤掉了一部分，却把**过滤前的原始序号**当作标题显示了出来。
这正好和 P0-2（D1）是同一个根因的另一种表现。

**建议**：与 P0-2 一并修（补齐步骤 + 序号重新连续编号）。

### P1-6（I2）发布包打开了 debuggable 开关

**现象**：`dumpsys package` 显示 `flags=[DEBUGGABLE ...]`，安装包带着 `android:debuggable="true"`。

**影响**：任何人可以通过 `adb run-as` 直接读取应用私有数据。本次测试正是借此导出了
全部 41 份菜谱、账号密码文件、烹饪历史记录。发布版本必须关闭该标志。

---

### P1-7（I5）11 个菜谱存在重复的选项 id

**现象**：同一个菜谱内出现完全相同的选项 id，共 11 个菜谱命中：

```
可乐鸡翅: kl_f1×2, kl_f2×2      小龙虾: xlx_f1×2, xlx_f2×2
干煸四季豆: gbsj_f1×2, gbsj_f2×2   酸菜鱼: scy_f1×2, scy_f2×2
鱼香肉丝: yx_v1×2, yx_v2×2        味噌汤: wct_i1×2
天妇罗: tfl_f1×2                 小炒黄牛肉: xc_f1×2
泡菜汤: pct_f1×2                 湘西外婆菜: wp_f1×2
虾饺皇: xjh_f1×2
```

选项 id 是"记下用户选了哪一项""按 id 找回标准答案算分"的主键。
同一菜谱内 id 重复，会导致选中项和得分对应错乱。

**建议**：修正数据，并加一条构建期校验：每个菜谱内 id 必须唯一。

---

### P1-8（I3）4 个菜谱的评分满分合计不是 100

**现象**：`凯撒沙拉`、`奶油蘑菇汤`、`椰子鸡火锅`、`腊味合蒸` 四道菜的
`scoring` 六个维度加起来是 **95** 分，其余 37 道是 100 分。

以凯撒沙拉为例：刀工 5 + 火候 5 + 调味 30 + 步骤顺序 20 + 时间效率 25 + 创意搭配 10 = 95。

**影响**：结果页写着"满分100分"，但这四道菜的分数天生拿不到满分，与其他菜不可比。
实测凯撒沙拉即使按标准选项全对也只有 85 分。

**建议**：把这四道菜的评分权重归一到 100。

---

### P1-9（I9 / G1）用户配置的默认值与界面选项对不上

**现象**：`user_config.json` 里 `spice_level` 默认值是 **"适中"**，
但个人信息页辣度的可选项只有 **不辣 / 微辣 / 中辣 / 重辣**，没有"适中"这一项。
界面只能靠默认选中第 3 项，于是高亮显示成"中辣"——用户从没选过，界面却告诉他选了中辣。

同一份配置里还有几个连带问题：
- `user_id=0`，而 `users.json` 里账号的 `user_id=1`，两处对不上；
- `profile.nickname` 是空字符串，但首页和个人页显示的是 `shared_prefs/user_prefs.xml`
  里的 `username`（=test），昵称其实有两套来源；
- 写盘时中文被转义成 `\uXXXX`（如 `\u9002\u4e2d`），说明序列化方式不保留中文。

**建议**：统一种子数据的默认值（要么给辣度加"适中"，要么默认值改成"中辣"）；
昵称只保留一套来源；`user_id` 与账号表对齐；JSON 序列化改用保留中文的方式。

---

### P1-10（G3）忌口输入未保存（与 P1-1 同因，单独列出便于定位）

在忌口输入框填入 `aaa,bbb,ccc` 并点保存后，`user_config.json` 的 `dislike` 仍是 `[]`。
与 P1-1 是同一个保存失效问题。**注**：本机中文无法通过 adb 输入，该项用 ASCII 验证的是
"逗号分隔解析 + 落盘"这条逻辑链，结论不受影响。

### P2-1（I10）难度分级只用到 1~3 档

41 道菜的 `difficulty` 取值分布是 `{1: 10, 2: 20, 3: 11}`，而界面按 ★★★★★ 五档渲染。
4 星和 5 星永远为空，所有菜看上去都是"简单到中等"，难度分级的区分度失效。

### 6.1 显式等待改造细节

原来用固定睡眠「等界面就绪」，既不快也不可靠。现在改成轮询条件、成立即返回：

```python
def until(pred, timeout=12.0, interval=0.15, desc="条件"):
    deadline = time.monotonic() + timeout
    while True:
        v = pred()                     # 条件成立
        if v:
            return v                   # 立刻返回，不浪费一秒
        if time.monotonic() >= deadline:
            raise WaitTimeout(f"等待超时 {timeout:g}s：{desc}")
        time.sleep(interval)           # 唯一的 sleep，且只作为轮询间隔
```

`time.sleep` 只保留在「轮询间隔」这一种用途上。等待被分成两档，按代价选用：

| 等待类型 | 探测方式 | 单次代价 | 用在哪 |
|---|---|---|---|
| 界面切换（`wait_focus`） | `dumpsys window` | **0.18s** | 进首页/列表/烹饪/结果页 |
| 元素/文字变化（`wait_ui`） | `uiautomator dump` | 2.4s | 分类切换、步骤推进、按钮置灰 |
| 文件落盘（`wait_file`） | `run-as cat` | 0.1s | 检查设置保存 |

### 6.2 提速的三件事（附实测数据）

先量了瓶颈再动手，不是凭感觉优化：

| 实测项 | 数值 |
|---|---|
| 一次 `uiautomator dump` | **2.4 秒** |
| 一次 `dumpsys window` | 0.18 秒 |
| `input swipe` 的实际滚动量相对手指位移 | **约 1.4 倍**（惯性放大） |

据此做了三件事：

1. **界面抓取改一次 adb 调用**：从「dump 到文件再 `cat`」改成
   `exec-out uiautomator dump /dev/tty`，省掉一次 adb 往返；
2. **同名帧复用（快照缓存）**：没有发生输入动作时复用上一次抓取的界面。
   一次用例里往往反复读同一屏，原来每次都重抓（2.4s×N），现在只抓一次。
   任何 `tap/swipe/back/input` 都会让缓存失效，不会读到旧数据；
3. **改掉最耗时的循环**：选选项原来「每点一个就重抓界面」，现在利用
   「选项在界面上的顺序与数据一致、且点单选不会引起重排」这一事实，
   在同一张快照上连续命中多个目标；滚动查找列表也改成每轮只抓一次
   （原来每轮抓两次做前后对比）。

顺带修掉一个隐蔽的正确性问题：滚动步长若大于可视窗口，惯性会一次滚过整个窗口、
**直接跳过条目**（实测 1250px 手指位移会跳掉一整屏）。现在按实测的 1.4 倍放大率
把手指位移限制在 900px，保证相邻两帧仍有约 450px 重叠。
